## Unresolved issues and limits

- Product support is API-specific. The cited 8.3.RC1 ExecuteGraphWithStreamAsync table excludes Atlas 200I/500 A2 inference products. An available Ascend device alone does not establish compatibility; match the exact product and SDK support tables.
- Failed-release retry semantics remain unverified. The cited free/destroy pages describe success and failure, but do not guarantee that every failure leaves a live, reusable handle or allocation. Stub tests prove our bookkeeping under their injected semantics, not recovery from arbitrary runtime faults. Validate supported error classes before claiming shutdown recovery complete.
- GEFinalize has a Status signature, but its [8.3.RC1 reference](https://www.hiascend.com/document/detail/zh/canncommercial/83RC1/API/ascendgraphapi/atlasgeapi_07_0087.html) supplies no return-value or recovery contract. Following the source audit, the wrapper now logs and preserves finalization failure and rejects subsequent session creation until process restart. This contains failure; it does not recover partially torn-down runtime state.
- Debug input/output reads now share `debug.cpp`, which drains producers even for host storage, checks copies before printing, and propagates failure from graph compute. The standalone copy suite injects failed drains/copies and checks that no checksum or value is printed; it also checks pending host writes. Revision `a790f59` passed the real SDK build and one CPU-compared device matmul with diagnostics enabled; real-runtime fault injection remains untested.
- This review does not establish ES builder signature compatibility, numerical correctness, all host-buffer asynchronous-copy constraints, or correctness with custom ACL contexts.
- Blocking-copy latency and throughput require paired device measurements. Documentation provides no performance result for this implementation. Follow [HARDWARE.md](HARDWARE.md); no local SDK downloads or hardware-free SDK builds are needed for this audit.

## Tiling and matmul follow-up, 2026-10-24

The local official GE clone at `3f1fd9f7ea4208e3e88255d0c5c55fed8097d845` documents `ge.tiling_schedule_optimize` as disabled by default in `docs/en/design/features/tiling_sink.md`; its feature table lists A2/A3 products. `api/atc/atc_flags.cc` also defines the default as `0`. This source revision is separate from the installed CANN 9.1.0 binaries, so the table alone does not prove installed-runtime behavior. The backend currently enables the option unconditionally. Disabling it experimentally on 310P3 did not fix the large-matmul failure; no claim that it causes that failure is justified.

The installed ES headers expose both BatchMatMulV3 and MatMulV3. Their presence does not establish executable operator support: the direct GE MatMulV3 probe failed on a missing registered datatype-inference function. The BatchMatMulV3 probe compiled but failed at execution for the large projection, while a small control passed. See [310P3 results](310P3-RESULTS.md) for the independent reproducer, exact shapes, and limits of these conclusions.

### Operator source and format requirements

The official [ops-nn repository](https://gitcode.com/cann/ops-nn) was cloned locally, separately from GE. Reviewed master `b4e71f8bee74fd278a77fa9699a7fa593ebd2569` and the `9.1.0` branch at `a452f1cfc5ed268cecd714673845e0dcafe3130f`. A release branch is a closer reference than master, but its HEAD is not proof of the source used to build the installed binaries.

- `matmul/batch_mat_mul_v3/op_host/batch_mat_mul_v3_def.cpp` registers two 310P combinations: FP16 NZ/NZ -> NZ and FP16 ND/NZ -> ND. In both, the right operand is FRACTAL_NZ. This agrees with the installed CANN 9.1.0 `opp/built-in/op_impl/ai_core/tbe/config/ascend310p/aic-ascend310p-ops-info-nn.json`. The master README also documents FP16 and right-operand NZ restrictions for Atlas inference products. The graph-level prototype describes 2-6 dimensions; rank two alone is not a documented misuse.
- Logical ND inputs are not sufficient evidence of violating the kernel format requirement. GE contains format-conversion machinery (`compiler/graph/common/trans_op_creator.cc`). Inspection of the final graph confirms that TransData converts the right operand to FP16 FRACTAL_NZ `[160,256,16,16]` from logical ND `[4096,2560]`, and BatchMatMulV3 consumes that tensor with `adj_x2=true`. Its left input and output remain FP16 ND. The small passing control uses the same format combination. Thus the observed graph meets the registered format contract; conversion data correctness and kernel tiling remain separate questions. Do not manually relabel ND storage as NZ.
- The 9.1.0 `MatmulV3BaseTiling::CheckDimsAligned310P` checks 32-byte alignment of M for ND input A and N for ND output, conditional on hardware capabilities. `BatchMatmulV3BaseTiling` inherits that base and calls its shape-attribute processing. This gives a concrete source rationale for some alignment handling, not a universal rule for every GE product or format. The failing FP16 M=16, N=4096 probe already satisfies these two alignment checks; more M padding is not an evidence-based fix.
- GE `graph_metadef/register/shape_inference.cc`, `InferDtypeByRegisteredFuncOrRule`, emits the observed MatMulV3 error when neither a registered datatype callback nor an IR dtype rule is available. The reviewed 9.1.0 MatMulV3 infershape file registers shape inference only; its graph prototype lists allowed types without a shared type-derivation symbol. This is consistent with the error, but does not prove which libraries were loaded in the installed process. BatchMatMulV3 succeeds through inference, so these source snippets alone cannot explain the different installed registration paths.
- `graph_metadef/graph/utils/op_desc_utils_ex.cc` prefers V1 inference when present and otherwise uses V2. `IGNORE_INFER_ERROR` converts a failed V2 result to `GRAPH_PARAM_INVALID`; it does not supply missing inference. Do not use it as a fix. Likewise, the reviewed MatMul-to-V3 fusion pass checks hardware capabilities; its existence does not prove V3 is a drop-in replacement for every product.

The final tensor descriptors and compiler tiling logs have now been compared with the passing control; the exception snapshot also contains the expected all-one inputs. See [310P3-RESULTS.md](310P3-RESULTS.md) for the exact values and limits. Current evidence does not justify a new shape gate, a manual NZ conversion in the backend, or a blanket claim that the installed SDK is defective.

### Local kernel trace after disconnect

The already available ops-nn master source maps the pre-220 architecture branch in `matmul/batch_mat_mul_v3/op_kernel/batch_mat_mul_v3.cpp` to `BatchMatMulCommonKernel` with `MM_CFG_VEC_ND2NZ`. Its common kernel initializes the matmul library, supplies a local UB workspace, and calls `IterateAll`. This puts library-side ND conversion and tile execution within the remaining investigation; it does not establish which instruction failed in the installed binary. The reviewed source is not a binary-to-source mapping.

The previously fetched 9.1.0 `MatmulV3BaseTiling::CalL1TilingV200` explicitly sets depths to 6 when either operand is ND, then derives both K steps as depth divided by the double-buffer count. The collected `depth=6, stepK=3` values therefore match source policy rather than unexplained backend options. The passing and failing probes share these values but differ in base tile sizes and contraction length. A source-only review cannot safely choose replacement tiling values. Preserve these as diagnostic hypotheses until the independent N/K experiments and exact installed-library inspection are available.

### Rank-two operator correction

The official ops-nn `matmul/mat_mul_v3/op_graph/mat_mul_proto_extend.h` declares MatMulV2 as a rank-two graph operator with `x1`, `x2`, optional `bias`/`offset_w`, and transpose attributes. On the installed 310P3/CANN 9.1.0, a direct graph using that interface passed both the small control and M=16, N=4096, K=2560. Its final compiled graph retains MatMulV2 and selects a `te_matmulv2` kernel, distinct from the failing BatchMatMulV3 path.

`mul-mat.cpp` now selects that rank-two interface only when both operands have rank two; higher-rank graphs keep BatchMatMulV3. `mul-mat-ge.cpp` bridges it into ES using the installed public `CompliantNodeBuilder` V2 IR-definition methods and checked input edges. This is needed because the SDK has no generated MatMulV2 ES wrapper, and backend graph assembly occurs before GE initialization loads the operator registry. The explicit definition follows the official prototype and leaves inference validation enabled. Cache emission version advances to 4.

The candidate passed the SDK build, all six standalone tests, all three previously failing projection fixtures, and 36 supported small-matmul CPU comparisons. This is an observed 310 fix for rank-two lowering; the underlying BatchMatMulV3 failure, higher-rank large matmuls, and 910 validation remain unresolved. Model validation is recorded separately in [310P3-RESULTS.md](310P3-RESULTS.md).

### Rotary-position lowering

The installed 310P `ops-info-transformer.json` advertises RotaryPositionEmbedding with FP16/FP32 ND inputs, but its interleaved tiling rejected NORMAL mode with `current soc does not support interleaved` (`rope_interleaved_tiling.cpp:353`). The existing NEOX lowering compiled at `[1,32,1,128]` but failed the isolated `[128,32,1,1]` CPU comparison with error `3.052770421`, while repeated model traces first diverged in `Qcur-0` with identical graph inputs. Moving RoPE to CPU removed the model's non-repeatable decode error. These are stronger constraints than the registry's general dtype list.

`rope.cpp` now constructs the rotation formula with Slice, Concat, Sub, Mul, Add and the existing sine/cosine tables. It uses canonical `[B,T,H,D]` order throughout, broadcasts the tables over heads/batches, and computes in F32 before the final output cast. NEOX rotates split halves; NORMAL rotates adjacent pairs. This avoids both the unsupported fused interleaved mode and the observed fused NEOX decode failure without adding head-count or product switches. Emission version advances to 5. Partial rotation, YaRN, frequency factors and offsets retain their existing rejection policy.
